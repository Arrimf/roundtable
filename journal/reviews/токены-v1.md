Дата: 2026-09-03. Вызов: параллельно шесть голосов, read-only, один и тот же пакет (ниже). Каналы: codex exec (medium), grok (medium), kimi -p (по пакету), deepseek-http (v4-pro, high), gemini-http (3.7-flash → каскад, high), claude -p (fable, high). Времена ответа: kimi rc=0 72s; claude rc=0 95s; deepseek rc=0 108s; codex rc=0 173s; gemini rc=0 237s; grok rc=0 258s.

## Вопрос (дословно)

```

Как устроено сейчас (факты, проверены по коду 2026-09-03):
1. РАУНДЫ (choir.py): каждая фаза — затравка (expand), слепой ответ (ask), виток критики (rebut), свод (summarize) — это СВЕЖИЙ процесс CLI каждого голоса без продолжения сессии. Голос claude стартует из каталога Choir/, и его CLI подхватывает Choir/CLAUDE.md и корневой CLAUDE.md (~14 000 токенов) на каждый вызов.
```

## Голос codex (запись дословно)

Главный резерв — убрать автоподгрузку больших инструкций и стабилизировать общие префиксы; продолжать сессии между фазами раунда нельзя.

**а)** В канале Codex известны три разные вещи. `codex exec resume <thread_id>` восстанавливает нить между свежими процессами; это уже правильно используется в `live.py`. Обычный `codex exec` сохраняет журнал сессии на диске, но новый вызов без `resume` его контекст не наследует. OpenAI автоматически кэширует подходящие длинные совпадающие префиксы; в Responses API есть `prompt_cache_key`, а для новых моделей — явные точки кэша. Поэтому свежий процесс сам по себе кэш не запрещает: важны байтово стабильное начало, та же модель и близкие по времени запросы. [Официальная документация OpenAI](https://developers.openai.com/api/reference/cli/resources/responses/methods/create) Однако Codex CLI не выставляет документированного флага `prompt_cache_key`; гарантировать попадание либо сохранить кэш локально Choir не может. `cached_tokens` CLI здесь также не показывает. Межпроцессного кэша результатов чтения файлов мне не известно: ОС может кэшировать страницы, но токены повторно прочитанного текста это не экономит.

**б)** `expand` не нужны версия CLI, полный устав и история раунда. `ask` нужны дословный вопрос Автора и единая затравка: повтор вопроса здесь необходим для обнаружения сужения ведущим. `rebut` нужны собственная позиция и проверяемые чужие доводы; автоматически пересказывать или выборочно выбрасывать ответы нельзя, но можно не слать служебные поля журнала, версии, повторённые инструкции и более старые витки, уже полностью заменённые новым содержательным витком. `summarize` достаточно дословного вопроса Автора, ответов и статусов; полную многословную затравку можно заменить её критериями и SHA.

**в)** Нельзя продолжать blind-сессию после `expand`, раскрывать незакрытую фазу через диск, давать голосам разные сокращённые пакеты, менять первичные записи либо хранить вместо них конспекты. Нельзя лишать контролёра 14.5 доступа к живым файлам или выдавать ему dossier. Архивная дословность и модельный вход — разные слои: экономить можно на входе, не переписывая журнал.

**г)** Первой мерой я бы запускал раундовый Claude из нейтрального каталога с коротким фазовым контрактом и явным read-only-доступом к проекту, исключив автоматические ~14 000 токенов `CLAUDE.md`. Оценка: 70–90% входа Claude и примерно 15–25% входных токенов шестиголосого раунда. Цена — отдельные проверки файлового доступа, контролёра и неизменности пакета.

СВОЯ ИДЕЯ: в журнале хранить для каждого вызова `input_sha`, `stable_prefix_sha` и фактические cached/input tokens; оптимизировать только по измеренному коэффициенту повторного чтения, а не по длине файлов.

## Голос grok (запись дословно)

Сначала сверю по коду, что именно кэшируется и шлётся в канале Grok, затем отвечу по четырём пунктам.Сначала сверю факты по коду и по своему каналу (кэш/сессии), потом отвечу по пунктам а–г.Проверяю ещё метрики `cache_read` у Grok и точный cwd раунда — от этого зависит оценка экономии.**Главный рычаг у Грока — не «магический prompt cache», а отказ от повторной автозагрузки `CLAUDE.md` на каждый свежий процесс и дельта вместо полного пакета после слепой фазы.**

**а)** В канале grok между вызовами реально есть: (1) **продолжение сессии** — `-c` / `--resume`, ключ — cwd (`live.py` уже так делает; `choir.py` — нет, каждый `ask_one` без `-c`); (2) **автозагрузка project rules** — с cwd=`Choir/` CLI поднимает корневой и `Choir/CLAUDE.md` (~57 KB) на старт сессии; (3) в метриках CLI есть `cache_read` / `cache_read_tokens` — значит сервер что-то читает из кэша. **Не знаю:** TTL и ключ этого кэша, переживает ли он свежий процесс, кэшируются ли именно rules, есть ли у API явный `cache_control` как у Anthropic. `~/.grok/models_cache.json` — каталог моделей, не промптов. Кэш чтения файлов между процессами не документирован; внутри сессии файлы можно не слать повторно текстом — они уже в нити.

**б)** Можно не слать: полные чужие ответы в `rebut` (сейчас до 6000 симв. × N — заменить выжимкой тезисов + sha полной записи в журнале); полную затравку в `summarize` (достаточно вопроса Автора + sha seed); повтор вопроса Автора, если seed уже в контексте сессии; версию CLI — только в метаданные журнала. `CLAUDE.md` голосу на раунде вер1 обычно не нужен целиком — нужен короткий общий протокол в самом пакете.

**в)** Нельзя трогать: свежий процесс на слепой фазе; бит-в-бит одинаковый пакет фазы всем (правило 1); дословность **в журнале** (правило 3) — ужимать можно только то, что уходит в следующий промпт; контролёра 14.5 и его доступ к файлам.

**г)** Первым: `ask_one` для grok/kimi/claude после `blind` — из **отдельного cwd голоса** с `-c`, в промпт только дельта витка; слепая фаза остаётся cold start. Оценка: **−25…40% input** на раунд с ≥1 `rebut` (у агентных CLI). Цена: отдельные cwd как в `live.py`, иначе `-c` склеит нити; риск утечки имён в историю — только дельта под метками А/Б/В.

СВОЯ ИДЕЯ: считать экономию не по длине промпта, а по доле `cache_read_tokens`/`input` в телеметрии grok на cold start с тем же префиксом rules — если cache hit уже высокий, резать `CLAUDE.md` почти ничего не даст, и тогда единственный выигрыш — дельта после слепоты.

## Голос kimi (запись дословно)

• ВЫВОД: главный резерв — не в кэшах вендоров (они и так работают или недоступны), а в перестановке байтов: резать повторную затравку и чужие ответы по цитатам, оставляя дословную запись в журнале, а не в промпте.

  а) Мой канал — kimi CLI с продолжением (`-c`) в комнате и свежим процессом в раундах. Что известно: у Moonshot API есть неявное кэширование префикса контекста на стороне сервера (context cache), оно срабатывает автоматически при совпадающем префиксе и удешевляет повторные запросы, но точные тарифы, TTL и минимальный размер кэшируемого блока я подтвердить не могу — это сторона сервера, из клиента не видна. Чего не знаю: включается ли оно для моего тарифа, переживает ли оно свежий процесс (должно — оно по содержимому, не по сессии), и есть ли у CLI свой кэш чтения файлов (почти наверняка нет). Вывод практический: префикс промпта должен быть СТАБИЛЬНЫМ между вызовами — тогда серверный кэш работает и без продолжения сессии.

  б) Не нужно посылать: в rebut — чужие ответы целиком, достаточно выдержек, к которым голос критикует, плюс списка тезисов; в summarize — полной затравки, хватает формулировки вопроса; повтор вопроса Автора в каждой фазе — достаточно ссылки «вопрос тот же»; CLAUDE.md на 14k токенов для фаз rebut/summarize — правила нужны в полном виде только при записи ответа; версии CLI и прочий служебный шум — однозначно не нужны нигде.

  в) Нельзя трогать: свежий процесс слепой фазы (это и есть слепота, кэш содержимого её не ломает — голос всё равно не видит чужих ответов); правило 1 — одинаковый пакет всем, резать надо одинаково для всех шести; правило 3 — дословная запись обязана сохраняться в файлах-ответах, сокращать можно только то, что уходит В промпт, не то, что пишется В журнал; контролёр на первоисточнике — резка цитат в rebut делает его ещё нужнее, его усиливать, а не ослаблять.

  г) Первая мера: в rebut заменить полные чужие ответы на «карту тезисов» (по 5–10 строк на голос, извлекает сводчик прошлой фазы) плюс полные тексты лежат рядом на диске для агентных голосов по требованию. Пакет rebut уменьшается с ~30–60k символов до ~5k; на шести голосах это 30–50% токенов раунда. Цена: риск, что карта исказит чужую позицию — лечится тем, что карту делает сам голос-автор тезисов в конце своего ответа (дописывает «мои тезисы: …»), искажение исключено по построению.

  СВОЯ ИДЕЯ: ввести «самосвод» — каждый голос в конце слепого ответа сам пишет свой сжатый блок-тезис фиксированного формата; дальше по фазам ходит только этот блок, а полный текст читают с диска лишь спорящие стороны — экономия растёт с ростом числа голосов и не требует доверия к чужому суммаризатору.

## Голос deepseek (запись дословно)

Главный резерв — перевести раунды с CLI на прямой API с общим слепым префиксом и prompt caching; это даёт ~60–70% экономии входных токенов на повторных фазах, не ломая слепоту.

а) Мой канал — Claude CLI. Точно известно: есть `--resume` и `--continue`, локальный кэш сессий в `~/.claude/`, но между свежими процессами он не переиспользуется. Anthropic API поддерживает prompt caching (TTL ~5 мин, чтение кэша значительно дешевле записи), однако в CLI между отдельными вызовами он, насколько мне известно, не сохраняется. Не уверен, включён ли prompt caching внутри Claude Code по умолчанию.

б) В rebut полные чужие ответы избыточны для критики сути, но их нельзя заменять пересказом из-за правила 3. В summarize полная затравка не нужна — достаточно вопроса и краткого исходного контекста. Голосу не нужно перечитывать CLAUDE.md при каждом вызове, если зафиксирован хэш файла. Версия CLI и повтор вопроса Автора не должны дублироваться.

в) Нельзя трогать: свежий процесс для слепоты (исключает `--resume` между фазами), одинаковый пакет всем голосам (правило 1), дословную запись ответов (правило 3) и доступ контролёра к первоисточнику (14.5). Оптимизировать можно только технический префикс, одинаковый для всех и не содержащий истории.

г) Первая мера: перевести вызовы голосов в `choir.py` с CLI на прямой API с явным prompt caching для системных инструкций и затравки. Экономия: 60–70% входных токенов на фазах rebut/summarize за счёт чтения кэша вместо полной записи. Цена: переработка вызовов, потеря агентного доступа к диску, который в этих фазах не нужен.

СВОЯ ИДЕЯ: ввести «слепой кэш-конверт» — перед фазой создавать симлинк на единый файл пакета с хэшем; голос обязан читать только этот файл, а обвязка сверяет хэш и отдаёт уже разогретый префикс без повторной загрузки, оставляя чат пустым.

## Голос gemini (запись дословно)

Главный резерв экономии без нарушения протокола — отключение тяжелого `CLAUDE.md` при свежих вызовах CLI и жесткое выравнивание структуры промптов под серверный Prompt Caching вендоров.

а) **Кэширование в канале Gemini/API**: Google Gemini поддерживает автоматическое контекстное кэширование (Implicit Prompt Caching) для совпадающих префиксов текста. При свежем HTTP-вызове кэш срабатывает на стороне сервера Gemini, если системный промпт и начало контекста байт-в-байт идентичны предыдущим запросам. Дискового/сессионного кэша на клиенте у API-моделей нет. У CLI-агентов (Claude, Codex) повторный запуск из рабочей папки насильно парсит `CLAUDE.md` (~14k токенов) на каждый свежий процесс.

б) **Избыточные данные по фазам**:
1) Файл `CLAUDE.md` (14k токенов) не нужен API-каналам (Gemini/DeepSeek) и избыточен для узких фаз.
2) В фазе `rebut`: повторение версий CLI-инструментов и полных системных инструкций.
3) В фазе `summarize`: полная первичная затравка (`expand`) — достаточно краткого исходного вопроса и ответов участников.

в) **Неприкосновенный периметр**:
1) Свежий процесс в фазе `ask` для абсолютной слепоты и независимости.
2) Идентичность пакета данных для всех участников в пределах фазы (Правило 1).
3) Дословная запись оригинальных ответов в итоговую ленту (Правило 3).
4) Проверки контролёра по первоисточнику (Правило 14.5).

г) **Первоочередная мера**: Запуск процессов `choir.py` из изолированной рабочей директории (без автоматического подхвата `CLAUDE.md`) с передачей минимального системного промпта (~300 токенов) с правилами фазы.
*Экономия*: 65–80% входящих токенов на каждом вызове раунда. *Цена*: нулевая для логики; требуется лишь явно передать формат вывода в мини-инструкции.

СВОЯ ИДЕЯ: Внедрить сквозную «канонизацию префиксов» (Prefix Alignment): формировать промпты фаз так, чтобы их заголовок и статические правила располагались в самом начале сообщения и были едины для всей системы — это принудительно включит серверный Prompt Caching у API-вендоров (Gemini/DeepSeek/Anthropic) даже между изолированными одноразовыми вызовами разных голосов.

## Голос claude (запись дословно)

**Вывод: свежий процесс не отменяет кэш — у Anthropic кэш живёт на сервере и бьётся по байтовому префиксу, поэтому главная экономия для моего канала — сделать префикс стабильным, а не сохранять сессию.**

**а) Что кэшируется у меня.** Известно точно: API Anthropic кэширует префикс промпта (system + начало диалога) при точном совпадении байт; чтение из кэша стоит около 10 % входной цены, TTL 5 минут, у ряда конфигураций час. Claude Code ставит точки кэша сам, и `claude -p` из нового процесса попадает в кэш, если системная часть совпала. Практически: CLAUDE.md обоих уровней плюс инструкции CLI (около 14 000 токенов) при четырёх вызовах за десять минут оплачиваются полностью один раз. Что ломает совпадение: снимок `git status` и подсказки памяти вставляются в первое сообщение и меняются между вызовами, как только дирижёр дописал `room.jsonl`. Не знаю: ставит ли `-p` точку кэша на самом промпте, какой TTL действует у этого аккаунта, кэшируется ли затравка в позиционном аргументе (`choir.py:480`) как часть префикса. Кэша чтения файлов на диске нет: перечитывание файла в новом процессе — новые токены.

**б) Лишнее по фазам.** В `summarize` не нужна полная затравка, достаточно исходного вопроса и критериев. В `rebut` нельзя резать чужие ответы содержательно, но можно не повторять затравку, а дать её sha.
