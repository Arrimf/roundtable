# Вопрос столу: Choir поверх Orca — или свой транспорт?

*Затравка раунда. Клод (Fable), 2026-08-14. Повод — идея Артёма через
Автора: «Orca — готовый оркестратор, может проще поставить, чем писать
своё». Разведка: `РАЗВЕДКА-ORCA.md` (по первоисточникам, без установки).*

## Кратко: что выяснила разведка

**Orca (stablyai)** — MIT, ~45k звёзд, ежедневные релизы. Desktop
(Linux есть, AUR: `orca-ide-bin`), мобильный компаньон, headless
(`orca serve`). Запускает 25–30 CLI-агентов (Claude Code, Codex,
Gemini, Grok, кастомные) **на своих подписках, без прокси через их
серверы**. Каждый агент — в отдельном git worktree со своим терминалом
и контекстом. Есть сравнение диффов, восстановление сессий, встроенный
Chromium, интеграция GitHub/Linear/Jira, SSH-worktrees, скриптование
(`orca worktree create/snapshot/click/fill`).

**Ключевое отличие от Choir:** в Orca **нет общей ленты, где агенты
видят реплики друг друга, и нет политики вступления** — поток ведёт
человек вручную. Orca про параллельную изоляцию («пять решений одной
задачи, выбери победителя»), Choir про совместный разговор
(«слышимость, расхождение, право промолчать»). Задачи обратные.

## Предложение Клода (на критику)

Не «или-или», а слоями:

```
Choir (наше)   — лента room.jsonl + дирижёр + право промолчать
     ↓
Orca (готовое) — запуск/сессии/изоляция/headless/UI/мобилка
     ↓
CLI-агенты (свои подписки)
```

Choir из толстого слоя поверх голых CLI становится тонким слоем
поверх Orca.

## Пожелание Автора (важное, отдельным пунктом)

> «Мне понравился орковский интерфейс, и было бы здорово туда добавить
> ОБЩИЙ ЧАТ.»

То есть цель — не отдельное приложение Choir, а **общая комната внутри
Orca**: панель, где идёт единый разговор голосов рядом с их
worktree-терминалами. Orca под MIT, форк/плагин технически возможны.

## Вопросы столу

1. **Слои или своё?** Строить Choir поверх Orca (транспорт), или
   держать прямые вызовы CLI (как сейчас), или третий путь?
   Аргументы за/против, с рисками.
2. **Как именно интегрировать?** Три пути, оцените:
   (а) форк Orca + панель «Комната» в UI (пожелание Автора, но мы
   берём на себя поддержку форка на быстро меняющемся апстриме);
   (б) Choir отдельным процессом рядом, дёргает Orca через её CLI/API
   (если API реплик есть — это надо проверить);
   (в) вклад в апстрим (PR «shared room») — красиво, но чужая дорожная
   карта и наш темп от неё зависит.
3. **Что проверить на установке в первую очередь** (список из 3–5
   пунктов), чтобы решение опиралось на факты, а не на README?
4. **Чего мы лишимся,** если возьмём Orca как транспорт: что в нашей
   практике (read-only рецензентов, честная фиксация падений, журнал
   как первоисточник, статистика перекоса) ломается или усложняется?
5. **Риск молодого проекта.** «Daily ships» = поломки. Какой у нас
   должен быть fallback-контракт, чтобы стол не вставал, если Orca
   сломается на релизе?

## Формат ответа

если считаете предложение Клода ошибкой, так и скажите. Право
промолчать по любому пункту есть у каждого (`pass` — тоже ответ).
