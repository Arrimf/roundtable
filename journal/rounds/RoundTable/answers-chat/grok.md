1. **Живой чат — не по умолчанию.**  
Независимость сейчас — главная ценность стола. Параллельные слепые ответы дают разброс, а не консенсус-по-инерции. «Живой чат» имеет смысл только как **опциональный режим** после фиксации первого раунда: для уточнений, спора по фактам, стыковки противоречий. Скорость обмена не перевешивает, если цель — разные углы, а не быстрый «один голос».  
**Вердикт: независимость важнее.** Живой канал — поверх, не вместо.

2. **Минимум механики, если чат всё же делать.**  
Дирижёр уже pull-опрашивает — этого достаточно как транспорта. Не нужен free-form поток «кто угодно кому угодно». Нужны:
- **жёсткие фазы** (seed → independent → optional revise → optional sign-off);
- **видимость чужих ответов только после своего** (или после дедлайна раунда);
- **лимит ревизий** (один второй проход, не бесконечный тред);
- **типы сообщений свои**, не CHECK Orca: `seed`, `answer`, `revise`, `verdict`, `signoff`, `timeout`, `refuse`.

Второй раунд «увидел чужие — уточни» — **не сговор**, если:
- первый ответ **заморожен** в логе и не переписывается;
- revise — отдельная запись со ссылкой на `parent_id` / `round`;
- правила: править можно только ошибку/пробел, не «подстроиться под большинство».

Без этих ограничений второй раунд — тихий конформизм.

3. **Чего не хватает в `room.jsonl`.**  
Уже есть время, раунд, голос, роль, статус, latency, текст. Для восстановления через месяц ещё:
- **id события** + **parent_id** / **reply_to** (граф, не лента);
- **версия схемы** и **версия choir**;
- **промпт/хэш затравки** (что именно видел агент);
- **модель + CLI + флаги** (не только «Grok»);
- **контекст, который видел** (видел ли чужие ответы: `visibility: blind|after_round|full`);
- **exit code / stderr-хвост** при fail/timeout;
- **wall-clock дедлайн** раунда и **причина статуса** (timeout vs refuse vs parse_error);
- **хэш текста** (целостность при правках руками).

Без parent_id и visibility через месяц непонятно: это независимый ответ или уже после чужих.

4. **Одну вещь, которую бы сломал.**  
**Скрытую централизацию смысла в дирижёре.** Риск не в SQLite и не в таймаутах, а в том, что `choir.py` станет **единственным источником правды о «что считается ответом»**: обрезка, ретраи, выбор «успешного» из нескольких попыток, тихая подмена промпта, разный контекст разным голосам «для удобства». Когда доверие вырастет, баг в фазах/видимости/ретраях будет выглядеть как «стол решил», хотя это артефакт оркестрации.  
**Защита:** immutable first answers, явные фазы в логе, одинаковый seed-байт-в-байт, никакого silent rewrite.
