# Разведка: Orca (stablyai) — не изобретаем ли мы велосипед?

*Клод (Fable), 2026-08-14. Повод — вопрос Артёма через Автора: «Orca —
уже написанный оркестратор, может проще поставить, чем писать Choir?»
Разведка по первоисточникам (README, onorca.dev, AUR), без установки.*

## Что такое Orca на самом деле

**ADE — Agent Development Environment** от Stably AI. MIT, бесплатен,
живой и очень популярный (44.9k звёзд, «daily ships»). Desktop
(macOS/Windows/Linux), мобильный компаньон (iOS/Android), headless на
VPS (`orca serve`). В AUR готов: `orca-ide-bin`, `onorca-bin`.

Что умеет:
- запускает **25–30+ CLI-агентов** — Claude Code, Codex, Gemini, Grok,
  Cursor CLI, OpenCode, Copilot и произвольные кастомные;
- **свои подписки, без прокси через их серверы** (важно: ключи и
  трафик не уходят третьей стороне);
- каждый агент — в **отдельном git worktree**: настоящий чекаут,
  свой терминал, свой контекст, никакого общего состояния;
- сравнение диффов, восстановление сессий, встроенный Chromium,
  Monaco-редактор, интеграция с GitHub/Linear/Jira, SSH-worktrees;
- скриптование: `orca worktree create / snapshot / click / fill`.

## Главное: Orca и Choir решают ОБРАТНЫЕ задачи

| | Orca | Choir |
|---|---|---|
| Цель | N агентов работают **не мешая друг другу** | N агентов ведут **один разговор** |
| Отношения | изоляция (worktree на агента) | слышимость (общая лента) |
| Итог | пять решений одной задачи → выбери победителя | реплики, расхождения, вердикты |
| Кто решает, кто говорит | человек вручную | **дирижёр** (политика вступления) |
| Право промолчать | нет такого понятия | событие `pass` |

Проверено по первоисточникам: **общей ленты, где агенты видят реплики
друг друга, в Orca нет; политики вступления/роутинга между агентами
нет** — поток ведёт человек. Это не упрёк: Orca честно про
параллельное кодирование, а не про разговор.

Значит ядро Choir — **лента-первоисточник, дирижёр, право промолчать,
триггер расхождения, честные `error`-события, счётчик перекоса** — в
Orca отсутствует целиком. Это ровно то, ради чего Choir и затевался.

## Но брать Orca стоит — как слой ниже

Всё, что мы НЕ хотели писать (и что сейчас делается руками), у Orca
готово: запуск агентов, сессии, параллелизм, изоляция, UI, headless,
мобильный доступ. Наша сегодняшняя боль в Cursor_W — оркестратор
вручную дёргает CLI через bash, ловит лимиты (у Kimi concurrency=1),
парсит выводы и раскладывает карточки — это ровно та работа, которую
Orca берёт на себя.

Предлагаемая архитектура вместо «или-или»:

```
Choir (наше)   — лента room.jsonl + дирижёр + политика вступления
     ↓ дёргает голоса
Orca (готовое) — запуск/сессии/изоляция/headless/UI/мобилка
     ↓
CLI-агенты (свои подписки)
```

Плюс запасной путь: если программного API Orca для реплик не хватит,
Choir остаётся с прямыми вызовами CLI (как сейчас), а Orca живёт
рядом как рабочая среда человека.

## Что проверить перед решением (дёшево, обратимо)

1. Поставить (`orca-ide-bin` из AUR — нужен sudo, это шаг Автора) и
   прогнать один реальный раунд стола: Codex + Grok + Kimi на одном
   вопросе.
2. Выяснить главное для интеграции: есть ли **программный API/CLI для
   отправки реплики агенту и чтения ответа** (не только worktree и
   UI-клики). От этого зависит, станет ли Orca транспортом Choir.
3. Проверить, тянет ли Orca **Kimi** как кастомного агента и как себя
   ведёт с его лимитом concurrency=1.
4. Оценить риск: проект очень молодой и быстро меняющийся —
   «daily ships» означает и поломки. Наши прямые вызовы CLI надёжны
   и остаются fallback'ом.

## Вывод одной строкой

Транспорт изобретать не надо — **Orca берём и пробуем**. Комнату
изобретать надо — **её ни у кого нет**, и «чуточку допилить Orca» тут
не выйдет: у него нет ни ленты, ни дирижёра. Choir может стать
тонким слоем поверх Orca вместо толстого поверх голых CLI — вот
реальная экономия от идеи Артёма.
