# ПОВОРОТ: у Orca уже есть слой обмена сообщениями между агентами

*Клод (Fable), 2026-08-14, после установки. **Признание: моя разведка
(`РАЗВЕДКА-ORCA.md`) была неполной**, и стол вынес вердикт на
неполных данных. README и сайт Orca описывают worktrees и UI и
НЕ УПОМИНАЮТ оркестрационный слой — он живёт внутри бинарника и в
`skill-guides/orchestration.md`. Проверено локально на v1.4.182.*

## Что обнаружилось фактически

`orca orchestration --help` (вывод с установленной сборки):

```
send               Send an inter-agent message
check              Check messages for a terminal
reply              Reply to a message
inbox              Show messages across (or for) recipients
ask                Ask the coordinator a question and block until answered
run-create/use/current/list/show   — Run как контейнер разговора
task-create/list/update            — задачи
dispatch / dispatch-show           — назначение задачи терминалу
worker-start/show/read/stop/abandon/release/retain/list  — надзор за воркерами
gate-create/resolve/list           — decision gates
reset                              — сброс состояния
```

Ключевое из гайда (`skill-guides/orchestration.md`):

- **Групповые адреса: `@all`, `@idle`, `@claude`, `@codex`, `@gemini`,
  `@grok`, `@cursor`, `@opencode`, `@droid`, `@worktree:<id>`** — то
  есть широковещание по голосам уже есть из коробки.
- `send --subject --body --type --thread-id --payload --json` —
  **тредированные** сообщения.
- `check [--wait] [--timeout-ms] [--json] [--ack <delivery_id>]` —
  чтение с блокировкой и FIFO-доставкой с подтверждением (до 50
  сообщений в пакете, пакет переигрывается до ack).
- `ask --question --options --timeout-ms` + `reply --id --body` —
  **блокирующий диалог**.
- Типы сообщений: `status`, `dispatch`, `worker_done`, `merge_ready`,
  `escalation`, `handoff`, **`question`**, `decision_gate`,
  `heartbeat`.
- Роли координатор/рабочий, Run → Task → Dispatch, статусы задач.
- Capabilities рантайма подтверждают: `orchestration.federation.v1`,
  `orchestration.federation-control-mail.v1`, `orchestration.contract.v1`.

Плюс: headless-рантайм поднялся (`orca serve`), отдаёт
`status --json`, слушает `ws://…:6768` и **имеет веб-клиент**
(`http://127.0.0.1:6768/web-index.html`) — то есть интерфейс Автора
доступен и в браузере, не только в десктопе.

## Что это меняет в вердикте стола

Стоп-кран проверки №1 из свода звучал так: «нет программного
"отправить реплику → получить ответ" — транспорт закрыт». **Он есть.**
Значит:

- Тезис Грока «публичный CLI = `worktree click/fill`, это автоматизация
  UI, а не протокол реплик» — **опровергнут фактом**: `orchestration
  send/check/ask/reply` это именно протокол реплик, с типами, тредами
  и подтверждением доставки.
- Тезис «примитив Orca — изоляция, общей ленты нет» — верен лишь
  наполовину: worktree изолирует ФАЙЛЫ, но `inbox`/`send @all` даёт
  общую шину СООБЩЕНИЙ поверх изоляции.
- Оценка «Choir = ~80% работы» пересматривается: доставка,
  адресация, треды, блокирующий ask, надзор за воркерами и decision
  gates — уже написаны и поддерживаются апстримом.

## Чего в Orca всё равно нет (наше остаётся)

1. **`pass` — право промолчать.** В списке типов нет ничего похожего:
   молчание там = отсутствие сообщения, а у нас это событие ленты.
2. **Дирижёр как политика.** Есть координатор-роль и ручные циклы, но
   нет автоматических правил вступления (по адресу / по расхождению /
   по ролям) и защит: лимит реплик подряд, детектор вежливого
   пинг-понга, потолок токенов на тему.
3. **Триггер расхождения** — главная ценность нашего стола.
4. **Статистика перекоса по авторам** (116 карточек Клода против 1
   Джемини — наш диагноз, их система его не считает).
5. **Журнал как версионируемый первоисточник.** У Orca — своя
   очередь/БД доставки; `room.jsonl` в git и «история не живёт только
   в чужой базе» остаётся нашим требованием (на этом сходились все).
6. **Честный `error` участника** как событие ленты (у них есть
   `escalation`/`worker_done`, но семантика другая).

## Предложение (на переголосование стола)

Choir перестаёт быть транспортом и лентой с нуля. Он становится:

```
Choir-дирижёр (наше, тонкое)
   политика вступления · pass · триггер расхождения ·
   статистика перекоса · зеркалирование в room.jsonl (git)
        ↓ orca orchestration send/check/ask/reply --json
Orca orchestration (готовое)  — доставка, адресация, треды, ack
        ↓
Голоса-агенты в терминалах Orca (свои подписки)
```

Пожелание Автора («общий чат в интерфейсе») закрывается ещё дешевле:
разговор уже идёт по шине Orca, а панель/веб-клиент его показывает.

## ПРОВЕРЕНО ЖИВЬЁМ (2026-08-14, v1.4.182) — три факта

> **ПОПРАВКА 2026-08-14 (после разбора Грока, см.
> `СВОД-ПЕРЕГОЛОСОВАНИЕ.md`): пункт 1 ниже сформулирован слишком
> сильно.** В базе `orchestration.db` после пробы: `messages: 1`,
> **`deliveries: 0`**, `from_handle` = координаторский терминал того
> же Run. Это письмо координатора самому себе, а НЕ обмен двух
> голосов. Доказано только то, что внешний процесс имеет доступ к
> CLI оркестрации; живой обмен агент→агент остаётся непроверенным.

**1. Дирижёр может жить снаружи. Подтверждено.** Обычный bash-вызов,
не агент и не терминал Orca, успешно: создал Run
(`orchestration run-create --objective` → `run_a05a07e2c99f`),
отправил сообщение (`send --to @all --subject --body --json` → ok,
`msg_d4972ac16fc1`), прочитал его назад (`inbox --limit --json`).
Значит наш дирижёр — обычный скрипт рядом, а не плагин внутри Orca.

**2. Формат сообщения почти совпадает с задуманным `room.jsonl`.**
Поля: `id, run_id, from_handle, to_handle, subject, body, type,
priority, thread_id, payload, read, sequence, created_at,
delivered_at, delivery_contract, sender_pane_key`. Есть монотонный
`sequence` (наш `id`), `created_at` (наш `ts`), `thread_id` (наш
`topic`/`reply_to`), `type` (наш `kind`). **Зеркалирование
`inbox --json` → `room.jsonl` в git реализуемо один-в-один** —
первоисточник остаётся нашим и версионируемым.

**3. Типы сообщений закрыты — произвольный `pass` НЕ проходит.**
`send --type pass` → `{"code":"invalid_argument"}`. Значит право
промолчать в их словаре не выражается: `pass` кодируем либо через
разрешённый тип + признак в `payload`, либо (честнее) как событие
НАШЕЙ ленты, которого в шине Orca нет. Это дополнительный аргумент
за то, что журнал остаётся нашим первоисточником, а не проекцией
чужой очереди.

**4. Безопасность — БЛОКЕР, а не «принять осознанно».** Три факта,
вместе они образуют проблему:

- `orca serve` слушает `0.0.0.0:6768`, машина видна в LAN как
  `192.168.1.33`; доступ прикрыт лишь pairing-токеном;
- **опции бинда на localhost НЕТ.** `serve --help`: есть `--port`,
  `--pairing-address`, `--mobile-pairing`, `--no-pairing`, и явно
  сказано: «`--pairing-address` changes only the client-advertised
  address». То есть рекламируемый адрес поменять можно, слушающий —
  нет;
- **без рантайма шина не работает вовсе:** при погашенном `serve`
  любая команда `orchestration` возвращает
  `{"code":"runtime_unavailable"}`. Значит «просто не поднимать
  сервер» (предложение Кими) — не вариант: без него нет и шины.

Вывод: пользоваться оркестрацией = держать открытый в LAN порт.
Лечится только снаружи: правило файрвола на 6768 (нужен sudo, шаг
Автора), либо network namespace/контейнер, либо `--no-pairing`
(проверить, что при этом остаётся доступным). **До закрытия порта
живые раунды с реальными репликами не гонять** — журнал стола не
должен лежать на LAN.

## Что проверить дальше (обязательно, до решения)

1. **Живой обмен:** поднять два терминала с разными агентами, послать
   `send --to @codex`, получить `check --json` — увидеть текст
   реально доставленным (не только код возврата).
2. **Внешний процесс:** может ли НЕ-агент (наш скрипт-дирижёр)
   слать/читать через CLI, или адресация привязана к «терминалу
   агента» (`--terminal <handle>`)? От этого зависит, где живёт
   дирижёр.
3. **Экспорт истории:** можно ли выгрузить `inbox --json` целиком и
   зеркалить в `room.jsonl` — то есть сохранить первоисточник в git.
4. **Kimi как кастомный агент** и групповой адрес для него (в списке
   групп его нет — есть ли `@custom` / `--to run:<id>`).
5. **Безопасность:** `orca serve` забиндился на `0.0.0.0:6768`
   (advertised 127.0.0.1, есть pairing-токен) — для нашей практики
   «всё на 127.0.0.1» это надо либо ограничить, либо осознанно
   принять. **Отдельно проверить, что уходит в телеметрию** (вопрос
   Грока).

## Переголосование: Кодекс (первый ответ)

**Позицию меняет:** «Orca теперь подтверждённый сменный
runtime/транспорт, а не только UI-оболочка. Базовый тезис остаётся:
ядро Choir — наше». Довод «не доказан двусторонний API» снят; полный
round-trip «агент A → агент B → ответ» остаётся **приёмочным тестом,
а не стоп-краном**.

Минимальный Choir подтверждает: дирижёр (политика вступления,
расхождения, лимиты, `pass`, `error`, статистика) + зеркало
`inbox --json → room.jsonl`. Требование к зеркалу: сохранять исходный
envelope — `run_id`, `sequence`, `thread_id`, тип и **версию
адаптера**. Тонкий интерфейс транспорта и `direct-cli` fallback —
страховка (в логический минимум не входят, но желательны).

Три ловушки (его формулировки):

1. **`pass` нельзя слать притворной репликой.** Это локальное событие
   Choir: дирижёр фиксирует сознательное невступление, иначе
   отсутствие сообщения **неотличимо от таймаута/сбоя**.
2. **Очередь Orca — механизм доставки, не архив.** Нельзя `ack`-ать
   до записи в `room.jsonl`: возможна потеря. Порядок: записать →
   идемпотентно по `id/sequence` → потом `ack`; после сбоя уметь
   обработать дубль и обнаружить пропуск.
3. **`0.0.0.0:6768`** — реальная поверхность в LAN; pairing-токен
   снижает, но не отменяет риск. Для канона — bind на localhost или
   firewall; сетевой доступ включать осознанно, телеметрию проверить.

## Мораль (в протокол стола)

бинарнике). Стол потратил четыре голоса на вопрос, который был
