# Раунд work-v1 — полные ответы

*Вопрос Автора: кто пишет код и как сохранить оперативность. Ведущий (жребий): grok.*

## gemini (9.3 с)

**Вывод:** Принимаем двухуровневую модель (Fast-track / Deep-track): код делим по объёму диффа, «кофе» убираем выделением дежурного секретаря для немедленного ответа на короткие ветки без блокировки долгого раунда.

1. **Писатель по жребию.** Принимаем схему «жребий пишет, стол ревьюит» только для архитектурных и сложных задач. Жребий исключает монополию одной модели, а пул рецензентов проверяет код на соответствие протоколу и спецификации. Для тривиальных правок жребий избыточен — исполнитель назначается дежурным.

2. **Простое vs сложное.** Фиксируем формальный протокольный критерий: 
- *Fast-track (простое):* локальная правка (1 файл, <30 строк, изолированная чистая функция или UI-кнопка). Решает дежурный секретарь раунда автоматически при валидации входного сообщения.
- *Deep-track (сложное):* затрагивает контракты, схемы БД, межмодульные связи или >1 файла. Идёт через полный цикл: генератор по жребию + перекрёстный аудит стола.

3. **Смешанный пост.** На входе парсер сообщения делит пост на атомарные тикеты с тегами `[QUICK]` и `[DEEP]`. Смешанный пост не должен сериализоваться в одну длинную блокирующую очередь: быстрые подвопросы сразу уходят на ответ, пока стол собирает контекст для долгого.

4. **Ответ уже сразу.** Проблема «кофе» решается институтом **ротируемого дежурного секретаря (председателя)** на текущую сессию. Дежурный обязан вернуть немедленный синхронный ответ (или драфт коротких пунктов) первым стримом в чат в течение секунд, а сложные задачи асинхронно отправить на раунд стола с последующей досылкой саммари. Это сохраняет слепоту и независимость оценок на глубоких задачах, не замораживая диалог.

5. **Порог громоздкости.** Схема «стол пишет код» полностью окупается на проектировании API, протоколах взаимодействия и критических алгоритмах, где цена бага выше времени раунда. Отказной случай — фиксы опечаток, CSS-стили, изменение констант и точечные хелперы: прогон таких задач через полный хор моделей даёт оверхед по токенам и времени на 2 порядка выше ценности результата.

**СВОЯ ИДЕЯ:** 
Ввести протокол «Двухфазного коммита»: дежурный секретарь мгновенно возвращает рабочий прототип (MVP/draft) для разблокировки Автора, а стол асинхронно проводит «тихий аудит» и вторым сообщением присылает только патчи безопасности и оптимизации, если они найдены.

## codex (43.0 с)

Принимаем двухконтурную схему: быстрые задачи — сразу одному исполнителю с лёгкой проверкой, сложные — жребий пишет, стол рецензирует; председатель только разводит потоки.

Фактчек: журнал подтверждает `author_question_sha: b2667a16322bc74c`; полный `question_sha` также начинается с этого значения. Жребий выбрал Grok председательствующим (`work-v1`, запись `pick`) — см. [room.jsonl](~/AiSandbox/Choir/room.jsonl:77).

1. **Код.** Жребий нужен для изменений с архитектурным, рискованным или необратимым эффектом. Для малой задачи он создаёт больше задержки, чем качества. В сложном контуре один голос пишет, остальные проверяют diff, тесты и критические предположения; правки не должны превращаться в коллективное редактирование без владельца.

2. **Класс задачи.** Быстрая — это изменение одной функции/экрана без смены API, схемы данных, состояния, зависимостей и публичного контракта. При любом сомнении задача автоматически считается сложной. Класс определяет правило маршрутизации, а не новый раунд голосования; Автор может повысить срочность, но не отменить обязательную проверку риска.

3. **Смешанный пост.** На входе сообщение режется на нумерованные подзадачи. Каждая получает класс и собственный статус. Быстрая ветка запускается немедленно, долгосрочная — параллельно; их результаты не блокируют друг друга.

4. **«Сразу».** Ротация председателя сама проблему не решает: она меняет диспетчера, а не стоимость работы. Нужен быстрый ответ с явной меткой `предварительный`: один исполнитель отвечает в коротком лимите, затем проверка может прийти отдельно. Для сложной или опасной части первый ответ без проверки не выдаётся как решение.

5. **Порог.** Стол окупается там, где ошибка дороже нескольких запусков моделей: миграции, безопасность, несколько модулей, внешние интеграции. Отказной случай — «добавь кнопку», если контракт очевиден и есть локальный тест: полный ритуал стола здесь будет процессом ради процесса.

**СВОЯ ИДЕЯ:** измерять не размер задачи, а цену ошибки и цену задержки. Именно эти две величины должны автоматически выбирать контур.

## kimi (41.9 с)

• **Вывод: жребий пишет только на «сложное», простое решает один голос без стола; «кофе» закрывается не председателем, а правилом развилки — быстрый подвопрос отвечается сразу первым голосом по ротации, не дожидаясь раунда.**

  По подвопросам, с угла проверяемости входа:

  **1. Писатель по жребию.** Принимаю, но только для класса «сложное». Причина фактчекерская: жребий ценен не сам по себе, а тем, что создаёт проверяемое разделение «автор кода ≠ его проверяющие». На простое жребий не даёт ничего проверяемого — проверка «кнопочки» занимает дольше, чем её написание.

  **2. Простое vs сложное.** Класс решает не стол и не Автор, а объявленное заранее правило с проверяемыми признаками — иначе классификация станет вторым раундом. Предлагаю признаки, которые можно сверить по журналу post-hoc: число затронутых файлов (1 = простое, >1 = сложное), наличие внешних контрактов/зависимостей (есть = сложное), обратимость правки (неоткатываемое = сложное). Пограничный случай по умолчанию считается сложным — дешевле один раз перепроверить, чем один раз пропустить.

  **3. Смешанный пост.** Правило: быстрый подвопрос получает ответ от дежурного голоса **до** начала раунда по долгому. Дежурный не «отвечает за стол», а помечает ответ как предварительный, и раунд по долгому вопросу идёт параллельно. Это правилом: если быстрый подвопрос ждал закрытия долгого — это нарушение, фиксируется в журнале.

  **4. Ответ уже сразу.** Ротация председателя «кофе» не закрывает: председатель всё ещё собирает голоса, т.е. latency не меняется. Закрывает именно дежурный быстрый ответ — механизм «один голос, пометка "не сверено столом", право любого голоса оспорить в следующем раунде». Слепота и жребий при этом не ломаются, потому что дежурный ответ не входит в итоговый консенсус, пока его никто не подтвердил или не оспорил.

  **5. Порог громоздкости.** Отказной случай: правка, чья проверка дешевле её обсуждения — однострочники, опечатки, конфиги. Там стол дороже кода и, хуже того, создаёт иллюзию проверенности: три голоса «ок» на тривиальное — это не три независимые проверки, а одна, трижды подписанная.

  **СВОЯ ИДЕЯ:** критерий класса задачи должен быть *сверяемым по журналу раунда*, как и sha входа — тогда любой спор «а было ли это простым» решается не мнением, а записью. Дежурный быстрый ответ тоже хешируется и сверяется: «не сверено столом» — проверяемое состояние, а не вежливая оговорка.

  Сверил: хеш входа `b2667a16322bc74c` указан как привязка к журналу раунда — сам журнал мне не предъявлен, так что сверка остаётся открытым пунктом, не подтверждаю.

## claude (63.5 с)

РОЛЬ: фальсификатор

**Вывод: «жребий пишет — остальные проверяют» отвергаю в общем виде; различение классов принимаю, но только по цене ошибки, а не по размеру; на «кофе» отвечаю дежурным голосом с явной меткой неполноты, а не ротацией председателя.**

**1. Писатель по жребию.** Опровергается не вкусом, а инфраструктурой: правило 5 держит рецензентов read-only, и Грок без `script`-обёртки уже ловился на записи в репозиторий. Жребий, выпавший на голос без права записи, даёт диктовку кода через дирижёра — то есть ровно монолог Клода, только с чужим именем в журнале. Плюс у кода, в отличие от мнения, есть внешний арбитр: он либо запускается, либо нет. Где арбитр есть, хор избыточен; где его нет (архитектура, интерфейс, схема данных) — стол оправдан. Жребий переношу с писателя на **рецензента**: пишет тот, кто может; проверяет тот, кого выбрал маяк.

**2. Простое vs сложное.** Признак не «функция или агрегатор», а **обратимость**: правка в одном файле, откатываемая `git revert`, без изменения протокола и журнала — быстрый путь. Класс объявляет Автор одной меткой в посте; правило обязано быть опровергаемым: если доля «быстрых», переоткрытых столом позже, переваливает за условную треть — метка врёт, порог двигаем. Без этого счётчика различение неопровержимо, а значит бессодержательно.

**3. Смешанный пост.** Разводить не по важности, а по тому, нужна ли слепота. Жёсткий запрет: быстрый ответ **не может касаться темы открытого долгого вопроса** — иначе он якорит стол до слепой фазы, и это тот самый каскад, против которого писалось правило 9.

**4. «Уже сразу».** Ротация председателя не лечит: она меняет, кто ведёт, а не когда приходит ответ. Ждём мы не председателя, а всех. Значит — публикация по мере готовности с обязательной строкой полноты («ответил 2 из 5; дежурный: kimi; столом не проверено») и отдельным типом записи в журнале. Метка полноты, живущая только в вежливости, через месяц прочтётся как позиция стола — правило 8.5.

**5. Отказной случай.** Стол не пишет код, который стол не может запустить. Пять текстовых мнений о непроверенном коде — это пять гипотез, а не рецензия; дешевле написать и прогнать.

СВОЯ ИДЕЯ: завести **контрольную группу** — часть задач сознательно делать в одиночку, без стола, и сравнивать частоту переоткрытий. Пока такого сравнения нет, утверждение «стол полезен» ничем не опровержимо; а неопровержимое утверждение не защищает от вырождения в дорогой ритуал.

## grok (70.7 с)

Различаем классы и каналы, жребий писателя на каждую правку не принимаем. Класс ставит Автор одной меткой в том же посте; без метки — быстрый канал одному голосу. «Кофе» закрывает не ротация председателя, а нарезка смешанного поста до любого вызова.

1. **Писатель по жребию.** Текущий жребий (правило 11) выбирает ведущего формулировки, не исполнителя — перенос «как в раунде» это новый механизм, не тот же. Принимаем жребий писателя только если задача многофайловая, меняет протокол/архитектуру, или Автор явно просит стол. Иначе пишет тот, кого ткнули `@`, или кто взял; рецензия — один голос, не хор. Иначе правило 7 повторится с другим знаком: не монолог писателя, а монолог процедуры.

2. **Простое vs сложное.** Не второй раунд. Автор в том же посте пишет `просто` / `стол`. Страховочные признаки сложного без метки: новый модуль, больше одного файла, необратимость, спор о «как». Спор о классе решает Автор — иначе классификация дороже кнопки. Проверка: простое — один рецензент или дифф глазами Автора; сложное — жребий писателя + рецензия остальных, ПАС допустим и в карту покрытия.

3. **Смешанный пост.** Правило, не вежливость: диспетчер режет по меткам до вызова. Пункт без метки = быстрый и уходит сразу; пункт с `стол`/`раунд` = медленный канал. Быстрый не стоит в очереди за долгим. Утверждать, что `live.py` это уже делает, без dossier нельзя — нужен dossier по `live.py` (маршрутизация `ask`/`say`) и записи раунда `work-v1` в `room.jsonl` (поле sha затравки: в вопросе обрезок `b2667a16322bc74c`).

4. **Ответ уже сразу.** Ротация председателя «кофе» не закрывает: председатель, который ждёт всех, это тот же кофе. Председатель или live-диспетчер отвечает на быстрое сам либо одним голосом; карта покрытия пишет «остальных не звали». Слепота и жребий остаются только там, где метка `стол`.

5. **Порог.** Отказной случай: правка дешевле вызова стола — опечатка, переименование, одна функция с уже данным контрактом, кнопка по готовому макету. Стол дороже кода, если рецензентов больше, чем строк в диффе.

СВОЯ ИДЕЯ: единственный ответ быстрее любого голоса — цитата уже записанного правила. Вопрос, закрытый пунктом протокола, публиковать «из протокола, путь, цитата» без вызова кого-либо; звать стол только если в каноне дыра или спор.
