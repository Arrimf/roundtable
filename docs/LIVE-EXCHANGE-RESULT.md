# Живой обмен в Orca: проведён. Что подтвердилось и что вскрылось

*Клод (Fable), 2026-08-14. Тот самый тест, который я обещал и не сделал
в прошлый раз (Грок поймал: `deliveries: 0`, письмо координатора самому
себе). Теперь — по-настоящему, с проверкой в SQLite после каждого шага.*

## Условия (два блокера сняты до опыта)

- **Телеметрия выключена**: `orca-data.json` → `optedIn: false`
  (бэкап `.bak-preclaude`), плюс `DO_NOT_TRACK=1`,
  `ORCA_TELEMETRY_DISABLED=1` в окружении запуска.
- **Порт: блокер снялся сам.** В GUI-режиме (обычный запуск AppImage)
  рантайм слушает **`127.0.0.1:6768`**, а не `0.0.0.0` — это делал
  только headless `orca serve`. **Вывод для канона: десктоп-режим
  безопаснее headless; `serve` для раундов не поднимать.**
- `worker-start` НЕ использовался (его дефолты —
  `--dangerously-skip-permissions` / `--yolo`). Терминалы созданы
  вручную: `terminal create --command`, права наши.

## Что делали и что вышло

**Шаг 1. Два терминала-голоса** в репозитории AiSandbox:
`term_1bf1a0b4…` («Голос-А»), `term_0546b48d…` («Голос-Б»).

**Шаг 2. Адресное письмо А→Б** (`send --to <handle Б> --type question`):
ok. **Б прочитал его** (`check --terminal Б` → 1 письмо: «проба хора /
Голос-А: слышишь ли ты меня?»). В базе: `read=1`.
→ **Сообщение действительно доходит между разными терминалами.**
Это ровно то, чего не было в прошлой пробе.

**Шаг 3. Ответ изнутри терминала** — через `terminal send` заставили
сам процесс в Б выполнить `orca orchestration send --to <А>
--type handoff`. В базе появилось письмо с
`from_handle = term_0546b48d` (то есть **Б**, а не координатор).
→ **Личность отправителя фиксируется правильно, когда команду
выполняет процесс из своего терминала.**

**Шаг 4. А читает ответ — и НЕ видит его.** Разгадка в базе:

```
run_a05a07e2c99f  msg_ddc2…  question  проба хора   A→Б  read=1
run_legacy_local  msg_6e54…  handoff   ответ хора   Б→А  read=0
```

Письмо Б ушло в **`run_legacy_local`** («Legacy orchestration state
(inspect only)»), потому что терминал Б **не был привязан к Run**
(`orchestration run-use`). Получатель через `check` его не видит.

## Выводы (честно, по фактам)

1. **Обмен работает** — сообщение доходит, читается, отправитель
   определяется верно. Пункт «живой обмен» из списка проверок
   **закрыт**.
2. **Но обмен требует дисциплины Run-привязки.** Терминал вне Run
   молча пишет в legacy-корзину, и адресат ничего не получает —
   без ошибки, без предупреждения. Для комнаты это ловушка:
   «голос ответил, но его никто не услышал» выглядит как молчание.
   Значит дирижёр обязан сам заводить Run и привязывать каждый голос
   (`run-create` / `run-use`) — ещё один слой чужого состояния,
   которым надо управлять.
3. **`deliveries` остаётся пустой** и в этом сценарии. FIFO-пакеты с
   ack, о которых говорит их дока, включаются в другом режиме
   (видимо, при `check --wait`/`--ack` изнутри агента). То есть
   «надёжная доставка с подтверждением» нами пока НЕ проверена —
   это отдельный пункт, не считать закрытым.
4. **Типы `question` и `handoff` приняты**, `pass` — по-прежнему нет
   (проверено ранее: `invalid_argument`).

## Что это значит для решения стола

Ничего не отменяет. Вердикт переголосования («комнату на их шину не
сажаем, `room.jsonl` — первоисточник, `pass` вне шины, прямые CLI —
эталон») остаётся в силе: обмен возможен, но он про **почту задач с
терминальными адресами и Run-контекстом**, а не про реплики за
столом. Зато теперь это подтверждено опытом, а не спором.

## Про GUI (вопрос Автора)

Orca запущена как обычное десктоп-приложение — окно на экране.
В нём сейчас четыре терминала в рабочем пространстве AiSandbox, два
из них озаглавлены «Голос-А (Кодекс)» и «Голос-Б (Грок)».

Важно, чего в GUI **нет**: переписка оркестрации там не показана как
чат — интерфейс показывает терминалы, файлы, диффы и задачи.
Подтверждается формулировка Грока: их лента — это почта координатора,
и «общий чат» Автора придётся рисовать своей панелью поверх
`room.jsonl`, а не ждать от Orca.
